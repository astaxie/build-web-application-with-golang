# 3.1 Web'in çalışma prensipleri

Tarayıcınızı her açıp birkaç URL yazdığınızda ve enter'a bastığınızda ekranınızda güzel web sayfaları belirir. Peki bu basit işlemlerin arkasında neler olduğunu biliyor musunuz?

Normalde tarayıcınız bir istemcidir. Siz bir URL yazdıktan sonra tarayıcı URL'nin host kısmını alır ve host'un IP adresini öğrenmek için bunu bir Alan Adı Sunucusuna (DNS) gönderir. Ardından bu IP adresine bağlanır ve bir TCP bağlantısı kurulmasını ister. Tarayıcı HTTP isteklerini bu bağlantı üzerinden gönderir. Sunucu bu istekleri işler ve web sayfasını oluşturan içeriği barındıran HTTP cevaplarıyla karşılık verir. Son olarak tarayıcı web sayfasının gövdesini ekrana çizer ve sunucuyla olan bağlantısını keser.

![](images/3.1.web2.png?raw=true)

Şekil 3.1 Kullanıcıların bir web sitesini ziyaret etme süreci

Bir web sunucusu, diğer adıyla HTTP sunucusu, istemcilerle iletişim kurmak için HTTP protokolünü kullanır. Bütün web tarayıcıları istemci olarak kabul edilebilir.

Web'in çalışma prensiplerini şu adımlara ayırabiliriz:

- İstemci sunucuya bağlanmak için TCP/IP protokolünü kullanır.
- İstemci sunucuya HTTP istek paketleri gönderir.
- Sunucu istemciye HTTP cevap paketleri döner. İstenen kaynaklar dinamik betikler içeriyorsa sunucu önce betik motorunu çağırır.
- İstemci sunucuyla olan bağlantısını keser ve HTML'i ekrana çizmeye başlar.

Bu, HTTP işlemlerinin basit bir iş akışıdır -dikkat edin, sunucu veriyi istemcilere gönderdikten sonra bağlantılarını kapatır ve sonraki isteği bekler.

## URL ve DNS çözümlemesi

Web sayfalarına erişmek için her zaman URL kullanırız, peki URL'lerin nasıl çalıştığını biliyor musunuz?

URL'nin açılımı Uniform Resource Locator'dır (Tekdüzen Kaynak Konumlandırıcı). İnternet üzerindeki kaynakları tanımlamak için kullanılır ve temel biçimi aşağıdaki gibidir.

	scheme://host[:port#]/path/.../[?query-string][#anchor]
	scheme         temel alınan protokolü belirler (HTTP, HTTPS, FTP gibi)
	host           HTTP sunucusunun IP'si ya da alan adı
	port#          öntanımlı port 80'dir ve bu durumda yazılmayabilir.
			Başka portlar kullanmak isterseniz hangi portu kullandığınızı belirtmelisiniz. Örneğin,
			http://www.cnblogs.com:8080/
	path           kaynakların yolu
	query-string   sunucuya gönderilen veri
	anchor         çapa

DNS, Domain Name System'in (Alan Adı Sistemi) kısaltmasıdır. Bilgisayar ağ servisleri için kullanılan adlandırma sistemidir ve tıpkı bir çevirmen gibi alan adlarını gerçek IP adreslerine dönüştürür.

![](images/3.1.dns_hierachy.png?raw=true)

Şekil 3.2 DNS çalışma prensipleri

Çalışma prensibini daha iyi anlamak için ayrıntılı DNS çözümleme sürecine bakalım.

1. Tarayıcıya `www.qq.com` alan adını yazdıktan sonra işletim sistemi, bu alan adı için hosts dosyalarında herhangi bir eşleme ilişkisi olup olmadığını kontrol eder. Varsa alan adı çözümlemesi tamamlanmıştır.
2. hosts dosyalarında bir eşleme ilişkisi yoksa işletim sistemi DNS'te bir önbellek olup olmadığını kontrol eder. Varsa alan adı çözümlemesi tamamlanmıştır.
3. Hem hosts dosyasında hem de DNS önbelleğinde bir eşleme ilişkisi yoksa işletim sistemi, TCP/IP ayarlarınızdaki ilk DNS çözümleme sunucusunu bulur; bu büyük ihtimalle yerel DNS sunucunuzdur. Yerel DNS sunucusu sorguyu aldığında, sorgulamak istediğiniz alan adı kendi bölgesel kaynaklarının yerel yapılandırması içinde bulunuyorsa sonuçları istemciye döner. Bu DNS çözümlemesi yetkilidir (authoritative).
4. Yerel DNS sunucusu alan adını içermiyor fakat önbellekte bir eşleme ilişkisi varsa, yerel DNS sunucusu bu sonucu istemciye geri verir. Bu DNS çözümlemesi yetkili değildir.
5. Yerel DNS sunucusu bu alan adını ne bölgesel kaynak yapılandırmasıyla ne de önbellekle çözümleyebiliyorsa bir sonraki adıma geçer; bu adım yerel DNS sunucusunun ayarlarına bağlıdır.
-Yerel DNS sunucusunda yönlendirme (forwarding) etkin değilse, isteği kök DNS sunucusuna yönlendirir; kök sunucu da alan adını biliyor olabilecek bir üst düzey DNS sunucusunun IP adresini döner, bu örnekte `.com`. İlk üst düzey DNS sunucusu alan adını tanımıyorsa isteği yeniden bir sonraki üst düzey DNS sunucusuna yönlendirir ve bu, alan adını tanıyan bir sunucuya ulaşana kadar sürer. Ardından üst düzey DNS sunucusu, `www.qq.com` adresine karşılık gelen IP adresini bir sonraki düzeydeki DNS sunucusuna sorar.
-Yerel DNS sunucusunda yönlendirme etkinse isteği bir üst düzey DNS sunucusuna gönderir. Üst düzey DNS sunucusu da alan adını tanımıyorsa istek, alan adını tanıyan bir DNS sunucusuna ulaşana kadar daha üst düzeylere yönlendirilmeye devam eder.

Yerel DNS sunucusunda yönlendirme etkin olsun ya da olmasın, alan adının IP adresi daima yerel DNS sunucusuna döner ve yerel DNS sunucusu da onu istemciye geri gönderir.

![](images/3.1.dns_inquery.png?raw=true)

Şekil 3.3 DNS çözümleme iş akışı

`Özyinelemeli sorgu süreci (recursive query)` basitçe sorgulayanların süreç içinde değiştiği anlamına gelir. `Yinelemeli sorgu (iterative query)` süreçlerinde ise sorgulayanlar değişmez.

Artık istemcilerin en sonunda IP adreslerini elde ettiğini biliyoruz; yani tarayıcılar sunucularla IP adresleri üzerinden iletişim kuruyor.

## HTTP protokolü

HTTP protokolü, web servislerinin çekirdek parçasıdır. Web'in nasıl çalıştığını anlamadan önce HTTP protokolünün ne olduğunu bilmek önemlidir.

HTTP, tarayıcı ile web sunucusu arasındaki iletişimi kolaylaştırmak için kullanılan protokoldür. TCP protokolü üzerine kuruludur ve web sunucusu tarafında genellikle 80 portunu kullanır. İstek-cevap modelinden yararlanan bir protokoldür -istemciler istek gönderir, sunucular cevap verir. HTTP protokolüne göre yeni bağlantıları daima istemciler kurar ve HTTP isteklerini sunuculara onlar gönderir. Sunucular istemcilere kendiliğinden bağlanamaz ya da geri çağırma (callback) bağlantısı kuramaz. İstemci ile sunucu arasındaki bağlantı iki taraftan biri tarafından kapatılabilir. Örneğin indirme isteğinizi ve HTTP bağlantınızı iptal edebilirsiniz; bu durumda tarayıcınız indirme bitmeden sunucuyla olan bağlantısını keser.

HTTP protokolü durumsuzdur (stateless); yani iki bağlantı da aynı istemciden gelse bile sunucunun bu ikisi arasındaki ilişkiden haberi olmaz. Bu sorunu çözmek için web uygulamaları, bağlantıların durumunu korumak amacıyla cookie (çerez) kullanır.

HTTP protokolü TCP protokolü üzerine kurulu olduğu için bütün TCP saldırıları sunucunuzdaki HTTP iletişimini etkileyecektir. SYN flooding, DoS ve DDoS saldırıları bu tür saldırılara örnektir.

### HTTP istek paketi (tarayıcı bilgisi)

İstek paketlerinin hepsi üç bölümden oluşur: istek satırı, istek başlığı ve gövde. Başlık ile gövde arasında bir boş satır bulunur.

	GET /domains/example/ HTTP/1.1      // istek satırı: istek methodu, URL, protokol ve sürümü
	Host：www.iana.org             // alan adı
	User-Agent：Mozilla/5.0 (Windows NT 6.1) AppleWebKit/537.4 (KHTML, like Gecko) Chrome/22.0.1229.94 Safari/537.4            // tarayıcı bilgisi
	Accept：text/html,application/xhtml+xml,application/xml;q=0.9,*/*;q=0.8    // istemcilerin kabul edebileceği mime
	Accept-Encoding：gzip,deflate,sdch     // akış sıkıştırma
	Accept-Charset：UTF-8,*;q=0.5      // istemci tarafındaki karakter kümesi
	// boş satır
	// gövde, istek kaynağının argümanları (örneğin POST içindeki argümanlar)

**Görüyoruz ki GET'in bir istek gövdesi yok, POST'un ise var.**

HTTP'de sunucularla iletişim kurmak için kullanabileceğiniz pek çok method vardır; GET, POST, PUT ve DELETE tipik olarak kullandığımız 4 temel methoddur. Bir URL, ağ üzerindeki bir kaynağı temsil eder; dolayısıyla bu 4 method, bu kaynaklar üzerinde yapılabilecek sorgulama, değiştirme, ekleme ve silme işlemlerini tanımlar. HTTP'de GET ve POST çok yaygın kullanılır. GET, URL'ye sorgu parametreleri ekleyebilir; URL ile parametreleri ayırmak için `?`, argümanların arasında ise `&` kullanılır, tıpkı `EditPosts.aspx?name=test1&id=123456` gibi. POST ise veriyi istek gövdesine koyar, çünkü tarayıcı URL'ye bir uzunluk sınırı uygular. Bu yüzden POST, GET'e göre çok daha fazla veri gönderebilir. Ayrıca kullanıcı adı ve şifre gönderirken bu tür bilgilerin URL'de görünmesini istemeyiz, bu yüzden onları görünmez tutmak için POST kullanırız.

### HTTP cevap paketi (sunucu bilgisi)

Cevap paketlerinde hangi bilgilerin bulunduğuna bakalım.

	HTTP/1.1 200 OK                     // durum satırı
	Server: nginx/1.0.8                 // sunucu makinesindeki web sunucusu yazılımı ve sürümü
	Date:Date: Tue, 30 Oct 2012 04:14:25 GMT        // cevap verilen zaman
	Content-Type: text/html             // cevaptaki veri türü
	Transfer-Encoding: chunked          // verinin parçalar halinde gönderildiği anlamına gelir
	Connection: keep-alive              // bağlantıyı canlı tut
	Content-Length: 90                  // gövdenin uzunluğu
	// boş satır
	<!DOCTYPE html PUBLIC "-//W3C//DTD XHTML 1.0 Transitional//EN"... // mesaj gövdesi

İlk satıra durum satırı denir. HTTP sürümünü, durum kodunu ve durum mesajını içerir.

Durum kodu, istemciye HTTP sunucusunun cevabının durumunu bildirir. HTTP/1.1'de 5 çeşit durum kodu tanımlanmıştır:

	- 1xx Bilgilendirme
	- 2xx Başarılı
	- 3xx Yönlendirme
	- 4xx İstemci Hatası
	- 5xx Sunucu Hatası

Cevap paketleriyle ilgili daha fazla örneğe bakalım. 200 sunucunun doğru şekilde cevap verdiği, 302 ise yönlendirme anlamına gelir.

### HTTP durumsuzdur ve Connection: keep-alive

Durumsuz terimi, sunucunun bir bağlantıyı sürdürme yeteneği olmadığı anlamına gelmez. Sadece sunucunun herhangi iki istek arasındaki ilişkiyi fark etmediği anlamına gelir.

HTTP/1.1'de Keep-alive öntanımlı olarak kullanılır. İstemcilerin başka istekleri varsa bunlar için aynı bağlantıyı kullanacaklardır.

Dikkat edin, Keep-alive bir bağlantıyı sonsuza kadar canlı tutamaz; bağlantının ne kadar süre canlı tutulacağı sınırını sunucuda çalışan uygulama belirler ve çoğu durumda bu sınırı yapılandırabilirsiniz.

## İstek örneği

![](images/3.1.web.png?raw=true)

Şekil 3.7 Bir web sayfasını açarken oluşan bütün paketler

Yukarıdaki resimden istemci ile sunucu arasındaki iletişim sürecinin tamamını görebiliyoruz. Listede pek çok kaynak dosyası olduğunu fark etmişsinizdir; bunlara statik dosyalar denir ve Go'nun bu dosyalar için özelleşmiş işleme yöntemleri vardır.

Bu, tarayıcıların en önemli işlevidir: bir URL için istek yapmak, web sunucularından veriyi almak ve ardından HTML'i ekrana çizmek. DOM içinde CSS ya da JS dosyaları gibi başka dosyalar bulursa, tarayıcılar bütün kaynaklar ekranınızda çizilip bitene kadar bu kaynakları sunucudan tekrar isteyecektir.

HTTP istek sayısını azaltmak, web sayfalarının yüklenme hızını artırmanın yollarından biridir. Yüklenmesi gereken CSS ve JS dosyalarının sayısını azaltarak hem istek gecikmelerini hem de web sunucularınızın üzerindeki baskıyı aynı anda azaltabilirsiniz.
